# AI開発基準

## このスキルの目的

VUILDにおけるAIプロダクト開発の品質基準・技術スタック・セキュリティ要件・ガバナンスを定めたマニュアル。
AI・テクノロジー部のエージェントが安全かつ効率的にAI開発を推進するための基準書。

| レイヤー | 推奨技術 | 備考 |

## 2. 開発プロセス

### 標準開発フロー
```
① 課題定義 → ② PoC → ③ 設計 → ④ 実装 → ⑤ テスト → ⑥ デプロイ → ⑦ 運用・改善
   (1日)     (1-2週)   (2-3日)   (1-2週)   (2-3日)    (1日)      (継続)
```

### 各フェーズの成果物

| フェーズ | 成果物 | 承認者 |
|---|---|---|
| ① 課題定義 | 1ページの課題定義書 | AI戦略プランナー石井 |
| ② PoC | 動作するプロトタイプ + 評価結果 | Engineering LEAD |
| ③ 設計 | アーキテクチャ図 + API仕様書 | システムアーキテクト岡田 |
| ④ 実装 | コード + テスト + ドキュメント | コードレビュー後 |
| ⑤ テスト | テスト結果レポート | QA完了 |
| ⑥ デプロイ | デプロイ完了確認 | システムアーキテクト岡田 |

## 3. LLM活用ガイドライン

### プロンプト設計原則
1. **明確な役割定義**: システムプロンプトでAIの役割を明確に指定
2. **構造化された入出力**: 入力フォーマットと期待する出力フォーマットを指定
3. **Few-shot例示**: 2〜3個の例を含めて品質を安定化
4. **ガードレール**: 不適切な出力を防ぐ制約条件を明記
5. **バージョン管理**: プロンプトもコードと同様にGit管理

### LLM利用時の注意事項
- **機密情報**: 顧客の個人情報・機密データをLLMに送信しない
- **ハルシネーション**: LLMの出力は必ず人間が検証する仕組みを組み込む
- **コスト管理**: API利用料の予算を設定し、月次でモニタリング
- **レート制限**: API呼び出しにレート制限とリトライ機構を実装

### 社内AI活用の適用領域

| 適用領域 | 具体例 | 期待効果 |
|---|---|---|
| 設計支援 | GH定義の自動生成支援 | 設計時間短縮 |
| 見積支援 | 過去データからの自動概算 | 見積作成時間短縮 |
| ドキュメント | 議事録自動生成・要約 | 事務作業削減 |
| 顧客対応 | FAQ自動回答・問い合わせ分類 | 対応時間短縮 |
| ナレッジ検索 | 社内情報のRAG検索 | 情報検索効率化 |

## 4. コーディング規約

### Python
```python
# ファイルヘッダー（必須）
"""
モジュール名: xxx
目的: xxxを実現する
作成者: VUILD AI Team
更新日: YYYY-MM-DD
"""

# 型ヒント（必須）
def calculate_cost(material_volume: float, unit_price: int) -> int:
    """材料費を計算する。

    Args:
        material_volume: 材料体積（m3）
        unit_price: 単価（円/m3）

    Returns:
        材料費（円）
    """
    return int(material_volume * unit_price)
```

### TypeScript
```typescript
// 型定義（必須）
interface Project {
  id: string;
  name: string;
  status: 'planning' | 'design' | 'manufacturing' | 'construction' | 'completed';
  budget: number;
  startDate: Date;
}
```

### 共通ルール
- **変数名**: 意図が明確な英語名（省略禁止、ただしループ変数のi,j,kは可）
- **関数**: 1関数1責務、20行以内が目安
- **コメント**: Why（なぜ）を書く。What（何を）はコード自体で表現
- **エラーハンドリング**: 外部との境界では必ず例外処理
- **ログ**: 重要な操作にはログ出力（INFO/WARN/ERROR）

## 5. セキュリティ要件

### 必須セキュリティ対策
| 対策 | 内容 | 対象 |
|---|---|---|
| 認証 | JWT or セッションベース認証 | 全Webアプリ |
| 認可 | ロールベースアクセス制御（RBAC） | 機密データへのアクセス |
| 暗号化 | HTTPS必須、保存データはAES-256 | 通信・保存 |
| 入力検証 | ホワイトリスト方式のバリデーション | ユーザー入力 |
| SQLインジェクション対策 | パラメータ化クエリの使用 | DB操作 |
| XSS対策 | 出力エスケープ | HTML出力 |
| API鍵管理 | 環境変数で管理、コードにハードコードしない | API連携 |
| ログ管理 | 個人情報をログに記録しない | 全システム |

### セキュリティチェックリスト（デプロイ前）
- [ ] API鍵がコードにハードコードされていない
- [ ] 認証・認可が実装されている
- [ ] 入力バリデーションが実装されている
- [ ] HTTPS接続が強制されている
- [ ] エラーメッセージに内部情報が露出していない
- [ ] 依存パッケージに既知の脆弱性がない
- [ ] ログに個人情報が記録されていない

## 6. テスト基準

| テスト種別 | カバレッジ目標 | ツール |
|---|---|---|
| ユニットテスト | 80%以上 | pytest, Jest |
| 統合テスト | 主要フロー100% | pytest, Playwright |
| E2Eテスト | クリティカルパス | Playwright |
| LLM出力テスト | 評価データセット10件以上 | カスタム評価スクリプト |

## 7. NG例・よくあるミス

| ミス | 影響 | 対策 |
|---|---|---|
| API鍵をGitにコミット | 鍵の漏洩 | .envで管理、.gitignoreに追加 |
| LLM出力を検証なしで表示 | 不適切な情報の表示 | 人間レビューまたはフィルタリング |
| テストなしでデプロイ | 本番障害 | CI/CDでテスト必須化 |
| エラーハンドリングなし | ユーザーに内部エラー表示 | 適切なエラーハンドリング実装 |
| ドキュメントなしで引渡し | 運用不能 | README + API仕様書を必須 |
| コスト監視なしでLLM運用 | 予算超過 | 月次のAPI利用料モニタリング |
